# 회의 안건 — 충전소 데이터 출처와 아파트·집 충전 처리 (2026-11-09)

작성: 장호연 요청으로 Claude 정리(2026-11-07 밤, `main` da23f34 기준). 회의용 문서이며, 기획서·코드는 아직 고치지 않았다.

## 한 줄 요약

기획서는 "충전소 목록 = 환경부 공공데이터 API를 서버에서 수집·캐시"라고 적었지만, **수집 코드는 아직 없고 지금 앱과 서버의 충전소는 전부 시연용 시드 10곳(판교)** 이다. 또 판정 규칙이 "150m 안에 등록 충전소가 있는가" 하나뿐이라 **아파트(입주민 전용) 충전기와 집 근처 충전**을 구분하지 못한다. 접수 마감(11-15) 전에 기획서 문구와 범위를 정해야 한다.

## 1. 지금 상태 (확인한 사실)

### 기획서·PRD에 적힌 것

- `docs/proposal.md` 5절 SDK/API 표: "F6 충전소 목록·상태 — 공공데이터포털 한국환경공단 전기차 충전소 API — **서버에서 수집·캐시**"
- `docs/proposal.md` 3절 기존 서비스 비교: "환경부 무공해차 통합누리집 … 차슐랭은 이 데이터를 목록의 기반으로 활용"
- `PRD.md` 136행: `stations` 테이블 = "id, 이름, 사업자, 좌표, 충전기 종류·출력(환경부 API)"
- `app/.../data/StationRepository.kt` 주석: "충전소 기본 정보(환경부 API 캐시, 서버 `stations`)"

### 실제 코드·서버

- 공공데이터포털 호출 코드, 인증키 설정, 수집 스크립트가 **저장소 어디에도 없다**(`data.go.kr`·`serviceKey` 검색 결과 0).
- 서버 테이블은 준비만 되어 있다: `server/supabase/migrations/20261102000100_initial_schema.sql`의 `stations`에 `external_id`, `source in ('PUBLIC_API','SEED')` 칸이 있다. **이용 제한·충전소 구분 칸은 없다.**
- 서버에 있는 충전소는 `20261102000200_demo_data.sql`의 **시드 10곳(st-001~010, 모두 `source='SEED'`)** 뿐이다. 11-07 `20261107000100_demo_names.sql`로 이름을 "삼평동 공영주차장 (시연)" 같은 지명으로 바꿨다("(시연)" 표시는 유지).
- 서버에 연결하지 못하면 앱은 `FakeStationRepository`의 하드코딩 4곳을 쓴다(이쪽 이름에는 "(시연)" 표시가 없다).
- 점수·리뷰·실패 기록도 시드(`SEED` 설치 42개, 충전 325건)이고, 리허설 기록은 `SIMULATED`로 쌓인다.

### 기획서의 시연 데이터 안내(7절)

> 배터리 잔량은 에뮬레이터 콘솔로 주입한 값이다. … 다른 차량의 충전 기록은 시연용 시드 데이터다.

**충전소 목록 자체가 시드라는 말은 없다.** 5절 표의 "서버에서 수집·캐시"와 같이 읽으면 이미 구현한 것으로 읽힌다.

### 판정 규칙(PRD 5.3, `ChargeSession.kt` `stationRadiusM = 150.0`)

- 인증·실패: 가장 가까운 충전소와 150m 이내
- 150m 안에 충전소가 없으면 `NOT_AT_STATION` → 기기에만 저장, 서버에 안 올림
- 충전소의 성격(공용/입주민 전용/개인)은 보지 않는다

## 2. 문제

### 문제 A. 충전소 데이터가 시드인데 기획서는 실데이터처럼 읽힌다

- 심사·PT에서 "실제 충전소 데이터는 어디서 오나요?"라고 물으면 답이 기획서와 다르다.
- 1차 합격 20팀은 PT에서 **실제 동작 시연이 필수**다(공식 사이트, 11-07 확인). 시드여도 괜찮지만 **시드라고 밝혀야** 한다(PRD 5.5 원칙과 같음).

### 문제 B. 아파트 충전기(입주민 전용)

- 아파트 단지 충전기 상당수가 환경부 데이터에 등록되어 있다. 지금 규칙이면 **서버에 올라가고 점수도 매겨진다.**
- 생기는 일
  1. 외부인은 못 쓰는 충전기라 점수가 다른 운전자에게 쓸모없다.
  2. 같은 차가 매일 같은 단지 충전기에 기록을 올린다 → 가명 ID여도 **사는 곳이 추정**된다. 기획서 5절 "정확한 주행 좌표는 저장하지 않는다"는 개인정보 설명과 부딪힌다.
  3. 한 사람(한 단지)이 그 충전기 점수를 거의 혼자 만든다.
- 환경부 데이터에는 **"이용자 제한 여부"와 "충전소 구분·상세 구분"** 항목이 있다(공공데이터포털 `한국환경공단_전기자동차 충전소 정보`, 데이터 번호 15076352 설명에서 확인. 정확한 필드명은 API 문서에서 다시 확인 필요). 지금 스키마·코드에는 이 값이 없다.

### 문제 C. 개인 충전기(단독주택 등) 근처 오인

- 개인 충전기는 환경부 목록에 없어서 보통은 `NOT_AT_STATION`으로 빠진다(정상).
- 단, **집에서 150m 안에 공용 충전소가 있으면** 집 충전이 그 충전소의 "인증 충전"으로 올라간다. 도심에서는 흔한 경우다.
- 결과: 남의 충전소 점수·평균 속도가 오염되고(집 완속 7kW가 급속 충전소 평균을 깎음), 문제 B와 같은 위치 노출이 생긴다.

## 3. 선택지

### 문제 A — 충전소 데이터

| 안 | 내용 | 작업량 | 비고 |
|---|---|---|---|
| A1. 문구만 정직하게 | 5절 표 "서버에서 수집·캐시" → "시연: 판교 시드 충전소 10곳 / 출시: 환경부 API 연동 예정", 7절 시연 데이터 안내에 "충전소 목록도 시드" 추가 | 문서 10분 + docx 재생성 | **최소한 이건 꼭** |
| A2. 실제 수집 붙이기 | 공공데이터포털 인증키 발급 → 판교 일대(또는 성남시) 충전소를 받아 `stations`에 `source='PUBLIC_API'`로 넣는 스크립트(1회 실행) | 반나절~1일 + 인증키 승인 대기 | 이용자 제한 값도 같이 받으면 문제 B 해결의 바탕. 시연 시드 점수와 실제 충전소를 어떻게 섞을지 정해야 함 |

### 문제 B·C — 아파트·집 충전

| 안 | 내용 | 막는 문제 | 작업량 |
|---|---|---|---|
| B1. 이용 제한 충전소는 서버에 안 올림 | 이용자 제한 = 있음인 충전소에서 한 충전은 `NOT_AT_STATION`처럼 기기에만 저장 | B | 스키마 칸 1개 + 판정 분기 1개(A2가 있어야 실제 동작) |
| B2. "여기가 집이에요" 등록 | 첫 집 충전 때 한 번 묻고 위치는 **기기에만** 저장. 그 반경 충전은 아예 안 올림 | B·C | 화면 1개 + 판정 분기. 서버 변경 없음 |
| B3. 같은 차 반복 반영 한도 | 같은 차·같은 충전소 기록은 점수에 예: 30일 1회만 반영 | B(점수 독점) | 서버 집계 SQL 수정 |
| B4. 출력 불일치 제외 | 계산 평균 kW가 충전소 최대 출력에 비해 지나치게 낮으면(예: 급속 충전소인데 11kW 이하) 점수 집계에서 제외 | C(오염) | 서버 집계 또는 판정 규칙 |
| B5. (발표용 확장안) 입주민 전용 모드 | 아파트 충전기는 같은 단지 입주민끼리만 고장 정보를 보는 기능으로 분리 | — | 기획서 6절 확장 계획에 한 줄 |

## 4. 회의에서 정할 것

1. **문제 A**: A1만 할지, A2까지 할지. A2를 하면 담당·인증키 발급 담당·기한(11-12 전?)
2. **문제 B·C**: 제출본에 무엇을 "구현"으로, 무엇을 "출시 계획"으로 적을지. 제안: B2(집 등록)는 가능하면 구현, B1·B3·B4는 기획서·PRD에 규칙으로 적고 출시 계획으로
3. **기획서 문구 수정 범위**: 5절 SDK/API 표, 5절 판정 규칙 표("충전소가 아닌 곳"에 이용 제한·집 등록 추가), 5절 개인정보, 7절 시연 데이터 안내 → 수정 후 `tools/build-proposal-docx.py`로 docx 재생성
4. **PT 예상 질문 답변**: "충전소 데이터는 실제인가요?", "집·아파트 충전은 어떻게 하나요?", "같은 사람이 계속 올리면 점수가 왜곡되지 않나요?"

## 6. 회의 결정 (2026-11-09 회의, 11-10 장호연 전달)

> 장호연(11-10): "일단 충전소 연결했는데 우리 DB에 없으면 개인 주소로 등록(비공개, 본인만 확인) 후 요청할 경우 등록 검토하는 걸로 / 아파트나 그런 것도 동일"

- **DB에 없는 곳에서 한 충전**: 그 위치를 운전자의 **개인 장소로 등록**한다. **비공개**이고 본인만 본다. 서버 점수·리뷰에는 넣지 않는다(지금 `NOT_AT_STATION`을 기기에만 두는 규칙의 연장)
- **공개 충전소로 등록 요청**: 운전자가 요청하면 팀이 검토해 충전소 DB에 넣는다. 자동으로 공개되지 않는다
- **아파트(입주민 전용) 등 공용이 아닌 충전기도 같은 방식**: 개인 장소(비공개)로 두고, 요청이 오면 검토
- 문제 A: A1(문구 정직화)은 11-09 반영 완료. 이번 제출에서 환경부 API 일괄 수집(A2)은 하지 않음. DB는 시드 + 요청 검토로 늘린다
- 아직 정하지 않은 것: 이번 제출에 구현할지 출시 계획으로만 적을지, 개인 장소 저장 위치(기기만/서버 비공개 칸), 요청 검토 담당, 기획서 반영 범위
