# 요청 로그 실측과 약관 문구 제안

확인일: 2026-11-09 / 담당: 황준용 / 대상: 차슐랭·크루즈브레이커 공용 Supabase

## 결론

**“서버에는 위치 좌표를 보관하지 않습니다”라는 포괄적인 문구는 수정해야 한다.** 정상 조회에서는 테스트 좌표가 수집 로그에 나타나지 않았지만, 숫자 좌표에 문자를 붙인 잘못된 입력은 PostgreSQL 오류 메시지에 그대로 남았다. 조회 함수가 위치 이력 행을 만들지 않는 사실과 운영 로그에 입력값이 남을 수 있는 사실을 구분해야 한다.

이 문서는 실측 결과와 문구 제안이다. 앱의 확정 약관, 동의 버전, 서버 설정은 변경하지 않았다.

## 검증 방법과 결과

- 실제 프로젝트에서 앱과 같은 POST JSON RPC 경로를 사용했다. 실제 차량 위치 대신 임의의 테스트 좌표를 사용했다.
- `pleos_nearby_stations`, `pleos_nearby_risk` 각각 정상 조회, 잘못된 반경, 잘못된 위도 타입, 잘못된 경도 타입을 검사했다. 인증 없는 요청과 잘못된 JSON을 추가했다.
- 재현 실행: `e61080ce-bea1-4cf2-88a4-361efd3d4a46`, 요청 시각 UTC 06:20:04~06:20:08 / 한국 시각 15:20:04~15:20:08. 최초 재현 이후 검증을 보강한 최종 10건 기준이다.
- Management API의 실제 `edge_logs`, `postgres_logs`, `postgrest_logs`를 조회했다. 모든 최종 요청 10건을 요청 식별자 등으로 API 로그와 대조했다. 의도적으로 발생시킨 테스트 경고도 PostgreSQL 로그에서 확인해 수집 동작을 교차 확인했다.
- 테스트용 익명 Auth 사용자 한 명은 검사 후 삭제했다. 설치·충전·리뷰·해제·통과 업무 기록은 생성하지 않았다. 토큰과 원시 운영 로그는 보고서에 저장하지 않았다.

| 경우 | 요청 수 | 응답 | 실제 로그 관찰 |
|---|---:|---|---|
| 정상 주변 조회 | 2 | 200 | 테스트 좌표 문자열 발견 안 됨 |
| 허용 범위를 벗어난 반경 | 2 | 400 / 22023 | 테스트 좌표 문자열 발견 안 됨 |
| 위도·경도의 숫자에 문자를 덧붙인 잘못된 타입 | 4 | 400 / 22P02 | PostgreSQL `event_message`에 해당 좌표 문자열 포함 |
| 인증 없음 | 1 | 401 | 테스트 좌표 문자열 발견 안 됨 |
| 잘못된 JSON | 1 | 400 / PGRST102 | 테스트 좌표 문자열 발견 안 됨 |

최종 10건 모두 API 로그에서는 테스트 좌표가 발견되지 않았다. 좌표가 나온 4건은 모두 PostgreSQL의 `invalid input syntax for type double precision` 오류였다. 예를 들어 임의 위도 `37.412731945`에 검사 문자를 덧붙여 보내면 그 문자열이 오류 메시지에 포함된다. **정상적인 숫자 좌표 요청도 통상 저장된다는 뜻은 아니다.** 다만 모든 오류 경로에서 원시 좌표가 절대 남지 않는다고 약속할 수 없음을 실제로 입증한다.

PostgREST 소스도 조회했지만 테스트 요청과 연결되는 좌표 로그는 찾지 못했다. 이 검사는 조회 RPC의 선택한 정상·오류 사례에 대한 시점별 관찰이며, 모든 입력·향후 설정·플랫폼 내부 로그 전체의 무기록 증명은 아니다.

### DB 설정 확인

관리 연결에서 다음 값을 확인했다. `authenticator`, `authenticated`, `anon`의 로그·pgaudit 관련 역할별 설정 덮어쓰기는 조회되지 않았다.

```text
log_statement = ddl
log_min_error_statement = error
log_parameter_max_length = -1
log_parameter_max_length_on_error = 0
log_min_duration_statement = -1
log_min_duration_sample = -1
pgaudit.log = none
```

`log_parameter_max_length_on_error=0`이어도 오류 메시지 자체가 잘못된 값을 인용할 수 있다. 바인딩 매개변수 출력 설정만으로 위 사례를 막는다고 판단하면 안 된다.

## 약관 문구 제안

### 1절: 위치 조회와 보관

차슐랭:

> 근처 충전소를 찾기 위해 현재 위치의 위도·경도를 서버로 전송하여 주변 충전소를 조회합니다. 조회에 사용한 좌표를 위치 이력으로 데이터베이스에 저장하지 않습니다. 다만 요청 처리 중 오류가 발생하면 오류 로그에 좌표 등 요청 값의 일부가 포함될 수 있습니다.

크루즈브레이커:

> 근처 크루즈 해제 다발 구간을 찾기 위해 현재 위치의 위도·경도를 서버로 전송하여 주변 구간을 조회합니다. 조회에 사용한 좌표를 위치 이력으로 데이터베이스에 저장하지 않습니다. 다만 요청 처리 중 오류가 발생하면 오류 로그에 좌표 등 요청 값의 일부가 포함될 수 있습니다.

이는 주변 조회 좌표에 관한 문구다. 크루즈브레이커의 격자 번호·방향 기록, 차슐랭의 충전소 ID·충전 기록에 관한 기존 설명은 별도 항목으로 유지한다.

### 2절: 운영 로그 항목 추가

> 서비스 운영·보안 및 오류 확인을 위해 접속 IP 주소, 요청 시각·경로, 처리 결과 등의 운영 로그가 생성됩니다. 잘못된 요청이나 오류가 발생하면 좌표 등 요청 값의 일부가 로그에 포함될 수 있습니다. 현재 사용하는 Supabase 무료 플랜의 API·데이터베이스 로그 보관 기간은 1일입니다.

수집 항목 표에도 `운영 로그(IP 주소, 요청 시각·경로, 처리 결과, 오류 발생 시 요청 값 일부)`와 목적 `서비스 운영·보안·오류 확인`, 저장 위치 `서버 운영 로그`를 추가한다. “누구인지 알 수 있는 정보는 받지 않습니다”는 문장도 IP 수집 사실과 충돌하지 않도록 다음처럼 구체화한다.

> 이름·전화번호·이메일·차대번호를 이용자에게 입력받지 않습니다. 서비스 기록은 가명 ID로 구분하며, 접속 과정에서 아래의 운영 로그가 생성됩니다.

기술적 주의: Free의 1일은 공식 요금표의 API·DB 로그 보관 범위다. Supabase의 모든 내부 운영·보안 정보가 정확히 24시간 후 완전 삭제된다는 뜻으로 확대하지 않는다. 이 점은 실제 삭제를 관찰한 결과가 아니라 공급자의 현재 정책을 확인한 결과다.

### 처리 위탁·국외 처리 설명

> 서비스 데이터베이스는 Supabase의 호주 시드니 리전에서 운영됩니다. 운영 로그는 Supabase의 안내에 따라 EU 데이터센터에서 수집·저장되며, 서비스 운영 과정에서 선택한 데이터베이스 리전 밖에서 처리될 수 있습니다.

현재 프로젝트의 실제 DB 리전은 `ap-southeast-2`다. Supabase 공식 FAQ는 주 처리자를 Supabase Pte. Ltd.(싱가포르), Supabase, Inc.(미국)를 운영·기술지원 법인으로 구분한다. 기존의 “Supabase, Inc.” 한 줄만으로 모든 처리 위치·수탁자를 설명하지 않도록 위탁·국외 이전 항목을 함께 정리해야 한다. EU 내 구체 국가 등 공식 자료로 확인하지 않은 값은 추정하여 넣지 않는다.

### 3절: 철회 시 삭제 범위 구분

> 동의를 철회하면 가명 ID에 연결된 서비스 기록은 기존 삭제 절차에 따라 삭제됩니다. 운영 로그는 서비스 기록과 별도로 관리되며 위에 안내한 로그 보관 정책이 적용됩니다.

이는 기존 업무 기록의 즉시 삭제와 운영 로그 보관을 구분하기 위한 제안이다. 현재 철회 RPC는 Supabase 운영 로그까지 개별적으로 삭제하지 않는다. 기존 철회 표시·동의 시각 유지 설명도 함께 유지해야 한다.

## 반영 권고

대표자에게 위 실측 결과와 문구를 전달해 두 앱에 같은 기준으로 반영한다. 확정 본문을 변경할 때는 각 `docs/terms-draft.md`, 앱의 `TermsText.kt`, `AppContainer`의 약관 버전을 함께 맞춘다. 이번 검증으로 요청 로그의 기술 확인은 완료했으며 문구 확정·앱 반영은 별도 후속 작업이다.
